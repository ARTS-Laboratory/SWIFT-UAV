SWIFT UAV · ARTS Lab · Software-in-the-loop (SITL) Session C · v0.3

Full flight from Owens Downtown (KCUB), with battery

ArduPlane flies the swift_6dof_sitl Simulink model through one AUTO mission: a takeoff roll on runway 13, climbing right turns, a fast leg, slow left circles, a descending spiral, a right-hand traffic pattern and an autoland with rollout. The Battery subsystem drains a simulated 12-cell (12S) 10 Ah pack the whole time and sends its voltage and current to ArduPlane, so every flight figure and the battery figures get data from the same run.

Battery estimate by leg (printed by swift_sitl_cub)

Planning estimate only: level-flight drag plus the climb or descent term, run through the same swift_battery_fcn the Simulink Battery block uses. Expect the flown numbers to differ by several percent. The low-battery failsafe (return to launch (RTL) at 8000 mAh used) should not fire: there is about 4000 mAh of margin.

P0Before you start~2 min

Run this once per session. The address can change after a reboot.

Find your Windows address Ubuntu

The Windows IP address as seen from the Windows Subsystem for Linux (WSL). MATLAB listens on it. Type it in the box in the top bar and every command below fills in.

ip route show | grep -i default | awk '{ print $3 }'

Check the files are in place Folder

Everything for this flight is in Aero Simulink\Simulink\ArduPilot_SITL, which has its own copy of every file it needs. The Standalone folder next to it is the model without ArduPilot, and nothing here uses it. Inside ArduPilot_SITL, check for:

models\swift_6dof_sitl.slx
params\swift_placeholder.m, swift_aero_matrix.m, swift_sitl_params.m
sitl\ap_json_step.m, swift_sitl_preflight.m, swift_sitl_cub.m (v0.2), swift_plot_flight.m (v0.3), swift_sitl_patch.m, swift_sitl_signcheck.m, swift_sitl.param, swift_sitl_batt.param
battery\swift_battery_add.m, swift_battery_fcn.m, swift_battery_plot.m
swift_setup.min the top of ArduPilot_SITL

swift_sitl_cub.param and swift_sitl_cub.waypoints don't need checking: swift_sitl_cub rewrites them in step P1-2. Older versions are in Simulink\delete\.

If swift_sitl_batt.param is missing, or step P1-2 prints a battery [FAIL], run swift_battery_add swift_6dof_sitl once (with the ArduPilot_SITL setup active), then go on.

P1MATLAB: set up and start the model~3 min

Order matters. swift_sitl_preflight rebuilds P and parks the aircraft facing north, so swift_sitl_cub must run after it to turn the aircraft onto runway 13.

Set up the folder and run the preflight MATLAB

swift_setup puts this folder's subfolders on the MATLAB path (the preflight lives in sitl\, so it can't be found before this), makes ArduPilot_SITL the active setup and switches Standalone off. The preflight then checks the model patch, the surface signs, the tilt table and User Datagram Protocol (UDP) port 9002.

cd('<repo>\simulation\ArduPilot_SITL')
swift_setup
swift_sitl_preflight('ADDR')
swift_setup should print ARDUPILOT_SITL is ACTIVE.
The red SITL-TEST propulsion line (90 N static, 35 m/s) is expected. The motor and propeller values from the spreadsheet can't get the aircraft off the ground.

Park on runway 13, check the battery, write the files MATLAB

Sets P.sitl.hdg0 = 125.55, rewrites the mission and landing files, and prints the battery check, the plan with a battery estimate for each leg, and the Ubuntu commands with your address filled in.

S = swift_sitl_cub('addr', 'ADDR');
Look for four [ OK ] lines under BATTERY CHECK, then Battery [EST] 100% -> 60%, about 12.4 km and 11.5 min, and P.sitl.hdg0 = 125.55 deg.

Open the model and press Run Simulink

The clock stays at 0 until ArduPlane connects. You have about 120 s to start P3.

open_system('swift_6dof_sitl')   % then press Run (green arrow); stop time is inf
After this step, don't run swift_placeholder, clear or swift_sitl_preflight. Each of them resets the heading to north, which sends the takeoff roll off the side of the runway, and puts the battery back to its defaults.

P2Ubuntu: copy the four files~1 min

Copy the parameters and the mission to your Linux home folder Ubuntu

Copy them again every time you re-run swift_sitl_cub.

D="/mnt/c/<repo>/simulation/ArduPilot_SITL/sitl"
cp "$D"/swift_sitl.param "$D"/swift_sitl_cub.param \
   "$D"/swift_sitl_batt.param "$D"/swift_sitl_vtail.param "$D"/swift_sitl_cub.waypoints ~/
ls -l ~/swift_sitl*

P3Launch ArduPlane and start the mission~2 min to takeoff

Start SITL with KCUB as home Ubuntu

-w wipes old parameters. The four files load in order, and later files win. The battery file goes last because BATT_MONITOR only takes effect at boot.

cd ~/ardupilot/ArduPlane
../Tools/autotest/sim_vehicle.py -v ArduPlane -f JSON:ADDR -N -w \
  --custom-location=33.9744563,-81.0019926,58.9,125.5 \
  --add-param-file=../Tools/autotest/models/plane.parm \
  --add-param-file=$HOME/swift_sitl.param \
  --add-param-file=$HOME/swift_sitl_cub.param \
  --add-param-file=$HOME/swift_sitl_batt.param \
  --add-param-file=$HOME/swift_sitl_vtail.param \
  --out=udp:ADDR:14550 --console --map

The Simulink clock starts moving and MATLAB prints Connected to ArduPlane. The map opens on Owens Downtown with the aircraft on the runway 13 threshold, nose to the southeast.

Connect Mission Planner (optional) Mission Planner

In the top right choose UDP, click Connect, and enter port 14550. The heads-up display (HUD) battery readout shows the model's pack. If UDP won't connect, use TCP to host 127.0.0.1, port 5762.

Wait for GPS, load the mission, check the settings MAVProxy

Wait 30–60 s for EKF3 IMU0 is using GPS. The extended Kalman filter (EKF) has to be using GPS before the aircraft will arm.

wp load ../../swift_sitl_cub.waypoints
wp list
param show RTL_AUTOLAND
param show BATT_MONITOR
param show BATT_CAPACITY
Expect 21 items (home plus 20), RTL_AUTOLAND 2, BATT_MONITOR 4 and BATT_CAPACITY 10000. The console's Batt field should read about 50 V.

Arm and go MAVProxy

mode FBWA
arm throttle
mode AUTO

The takeoff starts as soon as AUTO is set: full throttle, nose-wheel steering on the centreline, rotation at 19 m/s.

Battery check in the first 10 s: at full throttle the voltage should sag about 3 V and the current should climb toward 60 A. If the HUD sits at exactly 50.4 V and 0 A, this ArduPlane build is ignoring the battery data and using its own simulated battery (see Fixes). The Simulink battery still logs normally.

P4Watch the flight~11 min · hands off

Times are approximate from AUTO. MAVProxy prints Mission: n WP as each item starts. The amber lines are the battery estimate.

Takeoff roll and climb to 30 mitems 1–2 · 0:00–0:45

100% throttle, rotation at 19 m/s, then a straight climb at about 10° pitch.

Peak current ~59 A · pack sags to ~47 V · ~3% SOC

Climb-out and climbing right turnsitems 3–5 · ~0:45–4:00

Past the runway end to 50 m, then two right turns while climbing to 80 m and 100 m. Roll goes positive, up to the 35° limit.

25–30 A · down to ~87%

Fast leg at 27 m/sitems 6–7 · ~4:00–5:15

2 km level at 100 m. The highest airspeed of the run; pitch and angle of attack drop.

~27 A · down to ~81%

Slow down, two left circles, spiral downitems 8–10 · ~5:15–7:30

Airspeed falls to 22 m/s (1.22 × stall). Two left circles at 100 m with steady negative roll, then a spiral down to 60 m on the same 130 m circle.

~22 A in the circles, ~5 A in the spiral (lowest in flight) · ~75%

Return leg and left turns onto downwinditems 11–14 · ~7:30–10:00

Back to 23 m/s, then two left turns while stepping down to 50 m and 45 m.

18–22 A · ~66%

Pattern, approach and autolanditems 15–20 · ~10:00–11:30

22 m/s on the downwind leg at 40 m, right turn to base at 35 m, right turn to final at 28 m, 2° glide path. The flare starts at 3 m or 2 s before touchdown. Touchdown is about 200 m past the threshold, followed by the rollout. Disarming comes 20 s after touchdown.

~17 A on final, hotel load only on the rollout · ends near 60%

If something goes wrong in the air: mode RTL goes straight to the landing sequence (item 15), because RTL_AUTOLAND = 2. The battery failsafes trigger the same RTL. mode LOITER circles in place while you work out what to do.

P5End the session~1 min

Wait for the disarm MAVProxy

Let the aircraft roll to a stop and wait for Disarming motors. That gives the landing and battery plots a clean end.

Stop Simulink first Simulink

Press Stop. The logged signals, including out_batt, arrive in out. If you stop Ubuntu first, the model sits waiting for packets.

Then stop SITL Ubuntu

Press Ctrl + C in the sim_vehicle.py terminal, then disconnect Mission Planner.

Keep the run MATLAB

outC = out;   % keep a copy before the next Run overwrites it

P6Plot and check the data~2 min

Make every figure from one command MATLAB

This draws the flight, takeoff, landing and battery figures, prints both summaries, and saves the PNGs, signals.mat, summary.txt and battery_summary.txt to data\runs\sessionC_cub\.

R = swift_plot_flight(outC, 'tag', 'sessionC_cub', 'wp', S.wp_file);

If S is gone, use fullfile(fileparts(which('swift_sitl_cub')), 'swift_sitl_cub.waypoints') for 'wp'. The battery numbers are in R.batt.

Optional: overlay what ArduPilot wanted Mission Planner

Go to DataFlash Logs, download the newest .BIN file (from ~/ardupilot/ArduPlane/logs/), and choose Create Matlab File. Then:

R = swift_plot_flight(outC, 'tag', 'sessionC_cub', 'wp', S.wp_file, ...

FIXCommon problems

SymptomFix
Wrong files run, or Undefined function errorsswift_setup hasn't been run in this MATLAB session, or the Standalone setup is active. cd into ArduPilot_SITL and run swift_setup, then look for ARDUPILOT_SITL is ACTIVE.
Simulink clock never movesThe address is wrong or out of date, or port 9002 is in use. Check the address with ip route, press Stop, and redo P1-1 to P1-3.
Aircraft rolls off the side of the runwayThe heading was reset to north. Stop both sides and run swift_sitl_cub('addr', …) again after the preflight. Check that --custom-location ends in 125.5.
arm throttle refusedWait for EKF3 IMU0 is using GPS and read the pre-arm message in the console. arm throttle force is fine in SITL.
Armed and in AUTO, but nothing movesThe mission isn't loaded. Run wp list; if it's empty, run wp load again, then mode AUTO.
HUD battery stuck at 50.4 V / 0 AThis Plane-4.6.2 build ignores the battery data in the JSON link and uses SIM_BATT_VOLTAGE instead. The flight and the Simulink battery plots are unaffected, but ArduPlane's battery failsafe won't follow the model. Building ArduPilot master fixes this.
RTL partway through the flightA battery failsafe triggered. Check P.batt.SOC0 is 1 and that the console showed BATT_CAPACITY 10000. Wrong values usually mean swift_sitl_batt.param wasn't copied or loaded.
Battery figures missing, or no out_batt in this runRun swift_battery_add swift_6dof_sitl, then fly again. Also check Model Settings → Data Import/Export → "Single simulation output" is ticked.
No landing figureThe run was stopped before touchdown, or the aircraft never got airborne. Let it disarm before pressing Stop.
Lands short or longChange the touchdown x (the "Touchdown, runway 13" row) or the final altitude (28 m) in swift_sitl_cub.m, re-run it, and copy the files again.
Want to fly it againAfter the disarm: wp set 1, mode FBWA, arm throttle, mode AUTO. The battery carries on from where it ended, so for a clean log and a full pack, restart from P1.
Simulation only. KCUB sits under the Columbia (CAE) Class C airspace shelf. A real flight there would need airspace authorization.
