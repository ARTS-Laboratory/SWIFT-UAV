Archived guide. The step-by-step record of how Session D was first flown by hand (Nov 2026). Since then the files have moved (sitl/missions, sitl/ardupilot, sitl/run) and the whole procedure is one command: swift_run D. <repo> = where you cloned SWIFT-UAV. See docs/swift_run_README.txt.
SWIFT UAV · ARTS Lab · Software-in-the-loop (SITL) Session D · v0.2

Motor-validation flight from Owens Downtown (KCUB)

ArduPlane flies the swift_6dof_sitl Simulink model through one AUTO mission, now on the real MAD X7215 IPE 220KV motor with a 21x10 propeller, a 120 A electronic speed controller (ESC) and a 12-cell (12S) 10 Ah pack. The flight is a full-throttle takeoff roll, a fastest-rate climb to 120 m, five steady speed steps, a figure-8, a spiral down then a spiral up, a seven-gate slalom, and Session C's right-hand pattern and autoland. Between them the legs cover 30–100% throttle, so swift_motor_check can line the flight up against the MAD bench table.

Battery and throttle estimate by leg (printed by swift_sitl_cub_d)

Planning estimate only: drag plus the climb or descent term, turned into throttle by inverting the thrust table, and run through the same swift_battery_fcn the Simulink Battery block uses. Expect the flown numbers to differ by several percent. The low-battery failsafe (return to launch (RTL) at 8000 mAh used) should not fire: there is about 3700 mAh of margin.

P0Before you start~2 min

Run this once per session. The address can change after a reboot.

Find your Windows address Ubuntu

  1. Open the Ubuntu app from the Windows Start menu.
  2. Paste the line below (right-click pastes in the Ubuntu window) and press Enter.
  3. Type the address it prints into the Windows address box in the bar at the top of this page. Every command below fills it in.
ip route show | grep -i default | awk '{ print $3 }'

This is the Windows IP address as seen from the Windows Subsystem for Linux (WSL). MATLAB listens on it.

Check the files are in place Folder

In File Explorer, open <repo>\simulation\ArduPilot_SITL and check for:

models\swift_6dof_sitl.slx
params\swift_placeholder.m (v0.6, with the MAD X7215 table), swift_aero_matrix.m, swift_sitl_params.m
sitl\swift_sitl_cub_d.m (new), swift_motor_check.m (new, v0.2), swift_plot_flight.m (v0.5), swift_flight_events.m, swift_mark_events.m, swift_events_figure.m (new: numbered point markers), ap_json_step.m, swift_sitl_preflight.m, swift_sitl.param, swift_sitl_batt.param
battery\swift_battery_add.m, swift_battery_fcn.m, swift_battery_plot.m (v0.3)
swift_setup.min the top of ArduPilot_SITL

swift_sitl_cub_d.param and swift_sitl_cub_d.waypoints are already there, but swift_sitl_cub_d rewrites them in step P1-2 anyway. Session C's files are untouched.

If swift_sitl_batt.param is missing, or step P1-2 prints a battery [FAIL], run swift_battery_add swift_6dof_sitl once (with the ArduPilot_SITL setup active), then go on.

P1MATLAB: set up and start the model~3 min

Order matters. swift_sitl_preflight rebuilds P and parks the aircraft facing north, so swift_sitl_cub_d must run after it to turn the aircraft onto runway 13.

Set up the folder and run the preflight MATLAB

  1. Open MATLAB and click in the Command Window.
  2. Copy the block below, paste it with Ctrl+V, and press Enter.
cd('<repo>\simulation\ArduPilot_SITL')
swift_setup
swift_sitl_preflight('ADDR')
swift_setup should print ARDUPILOT_SITL is ACTIVE. The preflight's propulsion line should read MAD X7215 IPE 220KV, 145 N static, 32.9 m/s pitch speed.
If you see the red SITL-TEST propulsion line (90 N static) instead, this flight would test the old stand-in propeller, not your motor. Stop here and see Fixes.

Park on runway 13, check the battery, write the files MATLAB

Sets P.sitl.hdg0 = 125.55, rewrites the mission and parameter files, and prints the battery check, the leg-by-leg plan with estimated current, throttle and charge, and the Ubuntu commands with your address filled in.

S = swift_sitl_cub_d('addr', 'ADDR');
Look for [ OK ] lines under BATTERY CHECK, a thr % column running from 100 down to about 30, Battery [EST] 100% -> 57%, about 17.6 km and 15.4 min, and P.sitl.hdg0 = 125.55 deg.

Open the model and press Run Simulink

  1. Paste the line below into the Command Window and press Enter. The swift_6dof_sitl window opens.
  2. In that window, on the Simulation tab of the toolstrip, check Stop Time reads inf.
  3. Click the green Run button.
open_system('swift_6dof_sitl')

The clock in the bottom bar stays at 0 until ArduPlane connects. You have about 120 s to start P3.

After this step, don't run swift_placeholder, clear or swift_sitl_preflight. Each one resets the heading to north (the takeoff roll goes off the side of the runway) and puts the battery back to its defaults.

P2Ubuntu: copy the four files~1 min

Copy the parameters and the mission to your Linux home folder Ubuntu

  1. Click into the Ubuntu window.
  2. Paste the block below and press Enter.
  3. Check that ls lists four files with today's time, including swift_sitl_cub_d.param and swift_sitl_cub_d.waypoints.
D="/mnt/c/<repo>/simulation/ArduPilot_SITL/sitl"
cp "$D"/swift_sitl.param "$D"/swift_sitl_cub_d.param \
   "$D"/swift_sitl_batt.param "$D"/swift_sitl_vtail.param "$D"/swift_sitl_cub_d.waypoints ~/
ls -l ~/swift_sitl*

Copy them again every time you re-run swift_sitl_cub_d.

P3Launch ArduPlane and start the mission~2 min to takeoff

Start SITL with KCUB as home Ubuntu

-w wipes old parameters. The four files load in order, and later files win: swift_sitl_cub_d.param replaces the trim throttle (56 → 54%) and the maximum climb rate (1.1 → 2.0 m/s) from swift_sitl.param. The battery file goes last because BATT_MONITOR only takes effect at boot.

  1. In the same Ubuntu window, paste the block below and press Enter.
  2. Two new windows open: the MAVProxy Console and the Map. Type MAVProxy commands in the original Ubuntu window (the one showing STABILIZE> or MANUAL>).
cd ~/ardupilot/ArduPlane
../Tools/autotest/sim_vehicle.py -v ArduPlane -f JSON:ADDR -N -w \
  --custom-location=33.9744563,-81.0019926,58.9,125.5 \
  --add-param-file=../Tools/autotest/models/plane.parm \
  --add-param-file=$HOME/swift_sitl.param \
  --add-param-file=$HOME/swift_sitl_cub_d.param \
  --add-param-file=$HOME/swift_sitl_batt.param \
  --add-param-file=$HOME/swift_sitl_vtail.param \
  --out=udp:ADDR:14550 --console --map

The Simulink clock starts moving and MATLAB prints Connected to ArduPlane. The map opens on Owens Downtown with the aircraft on the runway 13 threshold, nose to the southeast.

Connect Mission Planner and set up the motor readouts (optional) Mission Planner

  1. Open Mission Planner. In the top right, set the connection drop-down to UDP, then click Connect.
  2. Type 14550 in the port box and click OK.
  3. On the Flight Data screen, click the Quick tab under the heads-up display (HUD).
  4. Double-click a value tile, tick current, and click away. Repeat for two more tiles with battery_voltage and ch3percent (throttle).

Now you can watch throttle, pack current and voltage step together through the staircase. If UDP won't connect, use TCP to host 127.0.0.1, port 5762.

Wait for GPS, load the mission, check the settings MAVProxy

  1. Watch the Console for EKF3 IMU0 is using GPS (30–60 s). The extended Kalman filter (EKF) has to be using GPS before the aircraft will arm.
  2. Paste the block below into the MAVProxy window and press Enter.
wp load ../../swift_sitl_cub_d.waypoints
wp list
param show TRIM_THROTTLE
param show TECS_CLMB_MAX
param show RTL_AUTOLAND
param show BATT_MONITOR
param show BATT_CAPACITY
Expect 38 items (home plus 37), TRIM_THROTTLE 54, TECS_CLMB_MAX 2, RTL_AUTOLAND 2, BATT_MONITOR 4 and BATT_CAPACITY 10000. The Console's Batt field should read about 50 V. The map should show the long test line and the slalom zig-zag southwest of the field.

Arm and go MAVProxy

mode FBWA
arm throttle
mode AUTO

The takeoff starts as soon as AUTO is set: full throttle, nose-wheel steering on the centreline, rotation at 19 m/s. With 145 N of static thrust it lifts off sooner than in Session C.

Battery check in the first 5 s: at full throttle the current should climb toward ~95 A and the pack should sag about 4–5 V. If the HUD sits at exactly 50.4 V and 0 A, this ArduPlane build is ignoring the battery data and using its own simulated battery (see Fixes). The Simulink battery, which swift_motor_check uses, still logs normally.

P5End the session~1 min

Wait for the disarm MAVProxy

Let the aircraft roll to a stop and wait for Disarming motors in the Console. That gives the landing and battery plots a clean end.

Stop Simulink first Simulink

In the swift_6dof_sitl window, click the red Stop button on the Simulation tab. The logged signals, including out_batt, arrive in out. If you stop Ubuntu first, the model sits waiting for packets.

Then stop SITL Ubuntu

Click into the sim_vehicle.py window and press Ctrl+C. The Console and Map windows close. In Mission Planner, click Disconnect.

outD = out;   % keep a copy before the next Run overwrites it

P6Plot and check the data~3 min

Make the flight and battery figures MATLAB

Draws the flight, takeoff, landing and battery figures plus the new flight events list, prints both summaries, and saves the PNGs, signals.mat, summary.txt, battery_summary.txt and events.csv to data\runs\sessionD_cub\.

Numbered points on every graph. Each mission item (timed from when the aircraft reached it) and each flight event (throttle up, liftoff, highest point, peak current, battery warnings, touchdown, stop) gets a number. The same numbers appear as dotted lines on the time plots, as circles on the ground tracks, and in swift_sitl_flight_events.png, which says what is happening at each one. Blue-grey = mission item, orange = flight event, red = battery. The summary printout ends with an Events line giving the count; expect about 34 for this flight.

Because S from P1-2 is still in the workspace, the plot scripts pick up the mission file and the leg names automatically. Add 'events', false to turn the markers off.

R = swift_plot_flight(outD, 'tag', 'sessionD_cub', 'wp', S.wp_file);

If S is gone, use fullfile(fileparts(which('swift_sitl_cub_d')), 'swift_sitl_cub_d.waypoints') for 'wp'.

Compare the motor with the bench table MATLAB

Finds every steady stretch of the flight (throttle, airspeed and climb rate flat, wings within 12° of level, at least 10 s long), prints them in a table, draws three figures, and saves motor_steady_points.csv and motor_summary.txt in the same run folder.

M = swift_motor_check(outD, 'tag', 'sessionD_cub');
Expect roughly 8–20 steady stretches, labelled S1, S2, … so they don't clash with the numbered points. They include the five staircase steps, the slalom legs and the pattern legs. The fl/mod column should be close to 100%: that confirms the Simulink build matches its own equations. The time-history figure carries the same numbered points as the flight figures.

Optional: overlay what ArduPilot wanted Ubuntu Mission Planner

The simulator writes its .BIN log inside Ubuntu (~/ardupilot/ArduPlane/logs/), not in Mission Planner's own Documents\Mission Planner\logs folder, so copy it out first.

  1. In Ubuntu (after Ctrl+C), paste the block below. The ls line shows the newest logs: the top one should have tonight's time and be tens of MB.
R="/mnt/c/<repo>/simulation/ArduPilot_SITL/data/runs/sessionD_cub"
mkdir -p "$R"
ls -lt ~/ardupilot/ArduPlane/logs/*.BIN | head -3
cp "$(ls -t ~/ardupilot/ArduPlane/logs/*.BIN | head -1)" "$R/sessionD_cub.BIN"
  1. In Mission Planner, click Flight Data, then the DataFlash Logs tab, then Create Matlab File.
  2. In the Open window, paste <repo>\simulation\ArduPilot_SITL\data\runs\sessionD_cub into the address bar, press Enter, pick sessionD_cub.BIN and click Open. The .mat file appears next to it, with a number added (e.g. sessionD_cub.BIN-1040581.mat).
  3. In MATLAB, put that file name in place of <name>:
d = fullfile(fileparts(fileparts(which('swift_plot_flight'))), 'data', 'runs', 'sessionD_cub');
R = swift_plot_flight(outD, 'tag', 'sessionD_cub', 'wp', S.wp_file, ...
                      'aplog', fullfile(d, '<name>.mat'));
No .BIN in that folder? sim_vehicle.py was started from a different folder. Find it with find ~ -name "*.BIN" -mmin -180 2>/dev/null, or open the folder in File Explorer with explorer.exe ~/ardupilot/ArduPlane/logs.

How to read the motor check: the MAD table was measured on a static test stand, so in flight every point should sit below it at the same throttle. That is expected, not an error. What matters is that the flight points sit on the model curve (fl/mod near 100%). The static gap to the bench, worst at full throttle, comes from the battery model's single efficiency value. True in-flight accuracy needs a logged flight of the real aircraft.

FIXCommon problems

SymptomFix
Preflight shows the red SITL-TEST propulsion lineP.sitl.prop is set to 'test'. Open params\swift_sitl_params.m, set the default prop to 'auto', save, and redo P1.
Wrong files run, or Undefined function errorsswift_setup hasn't been run in this MATLAB session, or the Standalone setup is active. cd into ArduPilot_SITL and run swift_setup, then look for ARDUPILOT_SITL is ACTIVE.
Simulink clock never movesThe address is wrong or out of date, or port 9002 is in use. Check the address with ip route, press Stop, and redo P1-1 to P1-3.
Aircraft rolls off the side of the runwayThe heading was reset to north. Stop both sides and run swift_sitl_cub_d('addr', …) again after the preflight. Check that --custom-location ends in 125.5.

arm throttle refusedWait for EKF3 IMU0 is using GPS and read the pre-arm message in the Console. arm throttle force is fine in SITL.
Climb to 90 m is slow (about 1 m/s)swift_sitl_cub_d.param wasn't loaded. param show TECS_CLMB_MAX should read 2. Recopy the files (P2) and relaunch.
Throttle hunts up and down on the staircase legsThe total energy control system (TECS) is still settling after the speed change. swift_motor_check only takes the flat part. If a step never settles, lower 'win' or 'min_s': swift_motor_check(outD, 'tag', 'sessionD_cub', 'min_s', 6).
No steady stretch foundSame as above, or the run stopped early. Try 'win', 5, 'min_s', 6.
Graphs have flight-event numbers but no mission items, or the events list has a Note saying the file doesn't matchS is missing or from another session. Pass the mission yourself: swift_plot_flight(outD, 'tag', 'sessionD_cub', 'wp', fullfile(fileparts(which('swift_sitl_cub_d')), 'swift_sitl_cub_d.waypoints')).
Too many markers to read on a busy plotUse the events list image to look up each number, or re-plot with 'events', false.
HUD battery stuck at 50.4 V / 0 AThis Plane-4.6.2 build ignores the battery data in the JSON link and uses SIM_BATT_VOLTAGE instead. The Simulink battery plots and the motor check are unaffected, but ArduPlane's battery failsafe won't follow the model. Building ArduPilot master fixes this.
RTL partway through the flightA battery failsafe triggered. Check P.batt.SOC0 is 1 and that BATT_CAPACITY showed 10000. Wrong values usually mean swift_sitl_batt.param wasn't copied or loaded.
Battery or motor figures missing, or no out_batt in this runRun swift_battery_add swift_6dof_sitl, then fly again. Also check Model Settings → Data Import/Export → "Single simulation output" is ticked.
Want to fly it againAfter the disarm: wp set 1, mode FBWA, arm throttle, mode AUTO. The battery carries on from where it ended, so for a clean log and a full pack, restart from P1.
Simulation only. KCUB sits under the Columbia (CAE) Class C airspace shelf, and the far legs are about 2.7 km from the field, beyond visual line of sight. A real flight would need airspace authorization and a different plan.
